# Every authored view, whole, on DataFusion against DuckDB (roadmap: rent what is not owned).
#
# `views` measures the fold sub-plans Burrmill owns. This measures the 22 CREATE VIEW statements
# in graph-allocations-nest as written, on the engine Burrmill intends to rent for everything
# else, with DuckDB on the same explicit file lists (no directory glob, roadmap 1.1), the same
# eight threads, and DuckDB's Parquet metadata cache ON - which `views` leaves off, and which is
# worth about 9% to DuckDB on the curation fold. Parity on sorted canonical-text rows is checked
# before any timing; a statement without it is never timed.
#
# A4's 65 statements were counted across every nest on the machine. This nest holds 22 of them,
# and it is the only nest with both segments and SQL views of any weight: dips-nest (2 views,
# 22 segments) is appended below; spookyswap-nest's one view file is comment-only.
#
# Tables declared in schema.json but never sealed (48 of 82) are registered EMPTY in both
# engines, which is what nuthatch serves for them. Every table a view names is one or the other.
#
# Three AST rewrites, applied to DataFusion's side only and named per statement:
#   hugeint    CAST(x AS HUGEINT) -> CAST(x AS DECIMAL(38,0))
#   intdiv     a // b -> CAST((a - a % b) / b AS DECIMAL(38,0)); DataFusion's decimal `/` carries
#              four extra digits and a plain cast back would round where DuckDB truncates
#   tuple-cmp  (a, b) > (c, d) -> a > c OR (a = c AND b > d)
#
# What does not run, and why:
#   ASOF JOIN (DuckDB syntax)          2 statements  sqlparser only knows Snowflake's MATCH_CONDITION form
#   [expr FOR x IN list] + lambda      3 statements  no list comprehension in the parser; list_reduce
#                                                    is not a DataFusion function even where it parses
#   port_queue                         1 statement   DataFusion's ambiguity rule: ORDER BY s.net_signal
#                                                    against a projected alias net_signal (nuthatch #996
#                                                    found the same)
#   cascades from the above            4 statements
#
# The DataFusion configuration is chosen and printed: ListingTable over one URL per file,
# collect_statistics=false (DuckDB collects none at plan time either), a 1 GiB footer cache so the
# working set fits. The DIAGNOSIS block then starts from DataFusion's own defaults (statistics on,
# 50 MiB cache, as `register_parquet` would) and changes one thing per row. The breakdown columns
# after plan+list are the plan's own metrics summed over partitions; file opens are async, so the
# sums overlap and rank costs rather than add up.
#
# Timing fairness, corrected before publication: the first run timed DuckDB through the
# parity path, which boxes, formats and sorts every cell, while DataFusion's time ended at Arrow
# batches. 600k rows of client-side string work were charged to DuckDB alone and the ratio read
# 0.60-0.64x. DuckDB is now timed through `query_arrow`, row count checked against the parity
# pass, which is what the numbers below are.
#
# Findings, in short:
#   - Under the chosen configuration DataFusion is 0.71x DuckDB time-weighted over the 11
#     statements that reach parity (2,856 ms against 4,028), ahead on 7 of 11. It loses on the
#     small-output statements (open_allocations 1.30x, epoch_boundaries 1.81x), where ~50 ms of
#     per-query listing shows, and on lodestar_allocations (1.23x). It is not 3.6x; that figure is
#     the synthetic fold through register_parquet, i.e. the defaults row below, and has not been
#     re-measured with the remedies.
#   - Under DataFusion's defaults the worst six are 2.06x DuckDB. Statistics collection reads every
#     footer at plan time (stats off: -41%); the default 50 MiB footer cache is below a
#     6-10k-segment table's working set and buys nothing over no cache at all (cache off: same);
#     sized to fit, it cuts footer time again (-26%). ListingTable then still `head`s every file at
#     plan time; a provider that already knows the file sizes removes that (-38%), landing the worst
#     six at 0.55x DuckDB. Pre-parsed footers from Burrmill's morsel cut match DataFusion's own
#     cache, so there is nothing left in footers. One file group and eight cost the same, so the
#     open path does not parallelise. What remains is per-file open and decode.
#
# Reproduce: cargo run -p burrmill-bench --release -- df-views /path/to/nest
# Measured 2026-09-16 on the MacBook, 8 threads, medians of 3 after a warm-up, one run per nest.
