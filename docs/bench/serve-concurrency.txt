# Roadmap 5.2: the concurrency sweep (RFC-0044 §3.5). MEASURED, AND IT IS NOT THE HEADLINE.
#
# §3.5 expected this to be 'the easiest headline in the project' because Burrmill takes no
# global lock. It is not. Properly-embedded DuckDB beats it under load on throughput, on tail
# latency and on fairness, and the reason is that Burrmill has no lock but does have a bounded
# shared pool - and a bounded pool with unfair scheduling starves clients just as effectively.
#
# Three arms, because 'DuckDB is slow under load' is only true of one way of embedding it:
#   duck_shared - one Connection behind a Mutex. What nuthatch does; what #986 measured.
#   duck_multi  - one database, one connection per client. DuckDB's own concurrent model.
#   burrmill    - one handle cloned; every client shares ONE 8-thread pool (roadmap 1.2c).
#
# worstp99 is the WORST CLIENT'S OWN p99, not a pooled percentile. Pooling weights by
# throughput, so a starved client contributes almost no samples and cannot move the number
# however badly it was treated: the first version of this reported 82 qps at 32 clients with a
# 14 ms p99, two figures that cannot both be true. The per-client counts said why - one client
# ran 191 queries and another ran none.
#
# fair = slowest client's query count / fastest client's. 1.00 is perfect sharing, 0.00 is a
# client that was never served at all.
#
# Reproduce: CLIENTS=1,4,16,32 SECONDS=5 burrmill-bench serve <fixture>
# 2026-08-31T15:04:11Z

## AFTER roadmap 5.3: a FIFO admission gate in front of the pool
############################################################################
#
# The starvation above was a liveness bug, not a slow queue: at a TWENTY second window one
# client still completed 220 queries while another completed none, having spent the whole
# window inside its first query. Rayon's workers prefer their local deques and visit the
# injector - where every queued query waits - only when those run dry, so under continuous
# load the queue can go unvisited indefinitely.
#
# The gate is a ticket lock with a width: admission is first-come-first-served and at most

## AFTER 5.5: the flush size was tuned at the wrong operating point
############################################################################
#
# 5.5 was filed as 'needs a scheduler'. Before costing one, the question was why a single
# query only gets 3.3x from eight threads. Answer: it depends on query SIZE. A 181 ms fold
# scales 7.9x; a 48 ms one scales 4x. Not per-segment cost - the speedup is the same with one
# segment as with two hundred - and not decode. It is LOCK CONTENTION on the aggregate's 64
# partitions, and it bites small queries because they flush proportionally more often.
#
# FLUSH_ROWS 4096 -> 16384 on a 500k-row query at 8 threads: scan 18 ms -> 11 ms, with the
# single-threaded cost unchanged at 50 ms. That signature - parallel time moves, serial time
# does not - is contention and nothing else.
#
# 4096 was chosen in roadmap 1.2 by sweeping a MILLION-group query on THIRTY-TWO threads,
# where memory was binding. A serving query is small and the constant is a contention knob
# there, not a memory one. The gate still passes: 218 MB, unchanged.
