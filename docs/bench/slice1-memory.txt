# Peak RSS at 1M groups, before and after roadmap 1.2.
#
# ONE MACHINE, ONE METRIC. A before-and-after across two machines and two different definitions of
# "RSS" is not a comparison, and the first version of these numbers was exactly that: the macOS
# harness read `ps -o rss=` (the process's RSS *right now*) while the Linux one read VmHWM (a true
# high-water mark). Peak in a fold happens while the aggregate and the answer are both live, so the
# development laptop systematically reported the friendlier number. Both now use getrusage.
#
# Box:      32-core Debian 6.12, 62 GB. `nproc` = 32.
# Fixture:  ROWS=2000000 SEGMENTS=100 ADDRS=1000000 -> 989,690 groups, 42-byte keys.
#           NEST-SHAPED, 12 columns (roadmap 1.1a). The `before` column below was measured on the
#           old 4-column fixture and is kept because the shape change it documents is far larger
#           than the fixture difference; the `after` column has been re-measured on the wide one.
# Measure:  peak RSS, operator only (no DuckDB linked, no DataFusion session), REPEATS=1,
#           median of three separate processes. Spread is +-3%.
# before:   commit eec0699, one aggregation per worker, Box<str> per output row.
# after:    one SharedAgg behind per-partition locks, answer keyed into the moved arenas.
#
# Gate: 256 MB **at 8 threads per query**, which the operator now enforces itself (roadmap 1.2c,
# decided 2026-08-31). `Limits::max_threads` defaults to 8 and the handle owns a pool that size, so
# peak RSS is a property of the query rather than of the host's core count.
#

# tighter because its allocator returns less, and that difference is worth knowing rather than
# averaging away.

# not a pass and it is not a comfortable fail, and saying which it is would be picking the run that
# suits. This is the sharpest argument for roadmap 1.2c: a gate with no stated parallelism cannot
# even be evaluated here.
#
# Widening the fixture to twelve columns did NOT cost memory, which is itself the projection
# pushdown working: three columns are decoded whatever the file holds.

# The wide-on-demand accumulator (roadmap 2.1b) cost NOTHING here: 210 MB before and after. An entry
# only carries a high word once its running total leaves i128, which on real data is never, so the
# order-independent refusal was free.
#
# agg_bytes, the aggregation's own live bytes, is 99 MB at EVERY thread count above. That is the
# whole claim of 1.2 stated as a measurement: the aggregate's size is a property of the data and not
# of the machine.

## How much of the peak is memory that is free but not returned

glibc holds a large free rather than handing it back, and the fold frees 57 MB of hash tables at
once when it turns the aggregate into rows. Forcing prompt return quantifies it. Three runs each,
stable to +-3 MB:

  threads   default   MALLOC_TRIM_THRESHOLD_=131072   retained
  8         208       172                             36 MB
  16        260       213                             47 MB
  32        338       271                             67 MB

So roughly 35-67 MB of the peak is retention rather than working set, and it grows with thread count.
It is still RSS and it still counts against the gate; the point of measuring it is that the remaining
overage is mostly NOT live data, so the next move is not "allocate less" - the tables have to exist
and then stop existing. A serving binary can remove it with one environment variable. The library
does not call `malloc_trim` itself: reaching into the host's allocator is not a library's business,
and it does not exist on macOS.

## REPEATS inflates peak RSS and must be 1 for this measurement

Retention accumulates across folds inside one process. Same code, 1M groups:

  threads   REPEATS=1   REPEATS=3
  8         208         274
  16        259         397
  32        349         507

## Decode scales far less than the aggregate does

With a trivial aggregate (509 groups) the same 2M-row scan costs 24 MB on one thread and 64 MB on
thirty-two - 1.3 MB per thread. At 989,690 groups the per-thread term is 5.6 MB. So the scaling is
not the Parquet decoder; it is concurrent hash-table growth and the freed memory behind it. That
measurement is why the fix was not "bound concurrent decode", which was the first guess.
