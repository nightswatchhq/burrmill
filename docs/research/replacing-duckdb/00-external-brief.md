## The brief, verbatim

# Burrmill vs DuckDB for Nuthatch: A Technical Brief on Where a Purpose-Built Rust Engine Can Actually Win

## TL;DR
- **Burrmill can be strictly better than DuckDB for Nuthatch on three axes that are structural, not incidental: exact ≥256-bit integer arithmetic with refuse-on-overflow (DuckDB's DECIMAL caps at 38 digits / INT128 — "Decimal256 (76 digits) is unsupported" per Spice.ai's DuckDB connector docs — and Nuthatch's `_dec` column already goes NULL on full-width uint256), owned execution over sealed-immutable segments (no MVCC, no buffer manager, precomputed zone maps), and build/deploy footprint (DuckDB ships as a 1.7 GB `libduckdb.a` C++ blob that forces a libstdc++ runtime dependency).** These are the wins to pursue; raw scan throughput on generic shapes is not.
- **The right target is "beat DuckDB on the admitted subset and delegate the rest," not full replacement.** Burrmill slice 1 already hits 0.38–0.87× DuckDB wall-clock at parity under 256 MB RSS on one plan shape (signed-union fold), and its differential corpus surfaced a DuckDB threaded-HUGEINT-SUM wrap that the exact-arithmetic story is built to prevent. But DuckDB's optimizer, join breadth, and SQL coverage remain far ahead, and Nuthatch's own RFC-0013 measured DataFusion 1.6–2.7× slower, so a naive Rust-native rewrite loses.
- **The 2026-08-30 keep-DuckDB decision (RFC-0042) should stay parked until Burrmill clears three falsifiable gates in sequence: (1) the hot/cold seam — redb tip ∪ sealed segments — at parity; (2) the build-footprint gate (burrmill#1) beating `libduckdb-sys` at `-g0`; (3) coverage of the top ~5 real query shapes from the Lodestar/allocations dashboards.** Reopening RFC-0042 is justified only when all three pass on a throwaway consumer crate, because the disk, binary-size, and correctness pains are the measured wins and the speed wins are conditional.

## Key Findings

**1. What Nuthatch actually sends to DuckDB is a narrow, well-characterised surface.** Nuthatch (now at v3.8.3 per its release tags, not the v2.5.x in the brief — the version has moved but the architecture is unchanged) uses DuckDB purely as a read-only analytical layer: it `ATTACH`es content-addressed sealed Parquet segments read-only, never writes through DuckDB, and the mutable tip lives in redb. The query surface is three front-ends over the same engine — the `/sql` HTTP route, the `nuthatch sql` CLI/REPL, and the MCP `sql` tool. The dominant SQL shapes are: `SUM(value_dec)` and `count(*)` aggregations, `GROUP BY` party/address folds, `ROW_NUMBER()` "newest row" picks, netted sums per entity (`Σ credit − Σ debit`), and whole-history `views/*.sql` folds evaluated at query time over hot ∪ sealed.

**2. The uint256 handling is already a visible compromise, and it is the single strongest argument for Burrmill.** Nuthatch stores `uint256`/`int256` as exact decimal text (VARCHAR), then offers a `{col}_dec` column that is `TRY_CAST(... AS DECIMAL(38,0))` — which yields NULL for any value beyond 38 digits — plus a `{col}_overflow` companion set to 1 when a contributing row could not be represented, precisely because `SUM` skips NULLs and would otherwise silently drop a real full-width uint256 from a total. DuckDB's DECIMAL maximum precision is 38 digits (INT128-backed; per DuckDB's Numeric Types docs, "the maximal supported WIDTH... is currently 38"); a uint256 needs up to 78 decimal digits. This is a hack Nuthatch has been forced into, documented in RFC-0047 and PR #1254.

**3. Nuthatch's issue tracker is a catalogue of DuckDB operational pain.** The most load-bearing: (#1183) every `/sql` request re-binds every authored view, so a bare `SELECT 1` cost ~1.2 s and opened ~32,000 files on the Lodestar nest because DuckDB binds views eagerly (strace showed 31,928 `openat`, 318,827 `fstat`, 318,423 failing `readlink`); (#1165) concurrent DuckDB instances overwrote each other's spill files and a nest segfaulted six times in twenty minutes at 2.0–2.8 GB peak on an 8 GB box under two concurrent queries; (#1186) whole-history folds recomputed on every request took 58.4 s for 47 dashboard statements; (#1428/#1429/burrmill#1) `libduckdb.a` is 1.7 GB of mostly DWARF and the 81 integration-test binaries each carry a ~250 MB DuckDB copy, ~8.9 GB of a 16.2 GB cold `target/`; plus two shipped security fixes for `/sql` filesystem escape (v0.9.3 arbitrary file read via quoted `read_csv`, v0.6.2 arbitrary file write via stacked `COPY … TO`). The Linux binary requires glibc ≥2.35 and libstdc++ `GLIBCXX_3.4.29`/`CXXABI_1.3.13` *because DuckDB is C++*.

**4. The Burrmill correctness claim is real and DuckDB-specific.** Burrmill's generated corpus, measured on `libduckdb-sys 1.10501.0` (which maps to DuckDB v1.5.1 under the post-1.5.0 scheme where the second semver component encodes the DuckDB version), found that crediting one party `i128::MAX` then `1` across two files with two threads makes DuckDB return `i128::MIN` for a `SUM` whose true value is `MAX+1` — a silent wrap — while the same query refuses correctly at one thread or over a single file, meaning the check is in the single-threaded path and missing from the partial-aggregate combine. I could not confirm this as an open issue in `duckdb/duckdb`; the documented policy is to error, and PR #15040 (Nov 2024, Mytherin) shows the team guarding HUGEINT/UHUGEINT sums against overflow-introducing optimizer rewrites ("No sum rewrite for hugeint/uhugeint since it could introduce overflow errors"). That means Burrmill likely found an unreported threaded-combine gap. It should be reported upstream regardless of the Burrmill decision.

## Details

### DuckDB's real weaknesses for *this* workload

- **256-bit integers and DECIMAL precision.** DuckDB's numeric ceiling for exact fixed-point is DECIMAL(38, scale), backed by INT128; there is no 256-bit decimal ("Decimal256 (76 digits) is unsupported," Spice.ai DuckDB connector docs) and HUGEINT/UHUGEINT are 128-bit (~38–39 digits). DuckDB does ship a `BIGNUM` (VARINT) arbitrary-precision *integer* type — per the Numeric Types docs, "A number with N decimal digits requires approximately 0.415 * N + 3 bytes when stored in a BIGNUM... the maximal and minimal representable values are approximately ±4.27e20201778" — but arithmetic on it is slow and Nuthatch does not use it. There is no arbitrary-precision *decimal*. For chain values that routinely exceed 38 digits, DuckDB has no exact native path — which is exactly why Nuthatch resorts to VARCHAR + `_dec` + `_overflow`.
- **Overflow semantics.** DuckDB is *better* than DataFusion here — DataFusion silently wraps integer arithmetic (`SELECT 10000000000 * 10000000000` yields `7766279631452241920`, and per Burrmill there is still no core config flag to stop it as of Aug 2026, issues #17539/#14771/#20034 open, with `%` erroring where `+` wraps) — but DuckDB is not watertight, per the threaded-HUGEINT-SUM finding above. Related documented defects: `AVG(DECIMAL)` on large values returns wrong results because the running mean goes through double (issue #6829 — corroborated by DuckDB's own `duckdb-decimal-arithmetic` extension, which exists to provide "Aggregate average on DECIMAL that returns a DECIMAL result instead of casting to DOUBLE"), and `PIVOT` with `SUM` on >20 columns coerces to HUGEINT despite explicit casts (issue #18007).
- **Startup / per-query overhead.** The #1183 eager-view-rebind pathology is the sharpest: DuckDB re-runs every `CREATE OR REPLACE VIEW` per request. On many small immutable segments, DuckDB's own Parquet Tips warn that per-row-group metadata reads add overhead and recommend row-groups ≥ thread count; reading footers across N files is N sequential round trips. Nuthatch works around all of this with a deterministic memo keyed on `(statement, row cap, sealed watermark, hot-store write_generation, entity watermarks, content stamps)` (PR #1189) — a cache that exists *because* the engine is expensive to invoke.
- **Memory / spilling / threading.** DuckDB spills past `max_memory` into `temp_directory` with filenames not keyed by instance (`duckdb_temp_storage_DEFAULT-0.tmp`), causing cross-instance corruption when Nuthatch runs several engines (#1165). Nuthatch caps it hard: `NUTHATCH_ANALYTICS_MEMORY_LIMIT` 512 MB, `NUTHATCH_ANALYTICS_THREADS` 2 (ceiling 16), and each connection's `max_memory` is `min(512 MB, 1 GB / live-permit-count)`. DuckDB runs its own thread pool, which sits awkwardly under a tokio host; the C-API serial-scan behaviour (issue #25632) means a C consumer cannot always opt into parallel scans without changing semantics (`preserve_insertion_order=false`).
- **Federation boundary.** DuckDB federates external data via replacement scans / Arrow zero-copy, but the redb hot tip is not a Parquet file — Nuthatch must bridge it, and every schema mismatch turns "zero-copy" into "low-copy" with fresh allocations. This seam is the highest-risk part of any Burrmill design (README: "the seam is the highest-risk invariant in the design").
- **Build / binary / cross-compile / FFI.** `libduckdb-sys` build dir is 3.4 GB; RFC-0042 §14 measured DuckDB at 10.6% of Nuthatch's clean Linux build time (vs 21.3% for wasmtime+cranelift), and disk + binary size were the only two of seven expected wins from dropping it that actually materialised. The C++ dependency forces libstdc++ linkage, complicates musl/aarch64 static cross-compilation, blocks a clean WASM target, and puts a segfault/panic-unsafe FFI boundary on the query path (the #1165 segfaults were memory over-commit crossing that boundary).

### What changed in the Rust ecosystem (relevant to the decision)

- **DataFusion.** Per the Apache DataFusion blog (Andrew Lamb, 2024-11-18), DataFusion 43.0.0 was "the fastest engine for querying Apache Parquet files in ClickBench... faster than both DuckDB and chDB/Clickhouse using the same hardware" (2024-11-16 hot run, 14 GB partitioned Parquet, 100 files ~140 MB, c6a.4xlarge), improving >30% over DataFusion 34→43 — **but the lead is contested by 2026** (DataFusion's own issue #14586 notes "DuckDB slipped past us in the most recent results"). More decisively for this workload: Nuthatch's RFC-0013 §5 measured DataFusion 1.6–2.7× slower on the fold that matters, gap widening with segment count, and Burrmill's own harness measured general DataFusion at 3.6× DuckDB at ten thousand segments (the many-small-files layout a nest produces) while beating DuckDB at high cardinality. Its silent integer wrap is disqualifying for a reference oracle. **Its real value to Burrmill is modular reuse: rent `datafusion-sql`/`datafusion-expr` for parsing/planning and own execution** — though burrmill#1 warns the DataFusion cold-path fallback is one of the heaviest trees in the ecosystem and must sit behind a feature flag the consumer can leave off.
- **arrow-rs / parquet-rs.** arrow 60.0.0 (Aug 2026) ships i256 in arrow-buffer (PR #11000, "Format i256 values without num-bigint," a −44.6% format speedup on Decimal256) and Decimal256 as a primitive with fixed casting; parquet's async `ParquetRecordBatchStream` was rewritten on a single PushDecoder (#8159) with a predicate-evaluation cache for filter pushdown, bloom-filter-from-dictionary population, and page-index support. **i256/Decimal256 are first-class — this is the substrate Burrmill's exact arithmetic should build on.** Note the arrow 56.0 breaking-change wave (Statistics/Metadata API removals) as a version-pinning hazard.
- **Vortex.** LFAI incubation project (formerly SpiralDB), file format declared stable from 0.36.0, claiming "100-200x faster random access reads than Apache Parquet; 2-10x faster scans with similar compression ratios and write throughput." Independent benchmarks (Daniel Beach, Data Engineering Central, Backblaze ~24 GB/184 files) found more modest gains: "the jump from CSV to any columnar format (~200×) dwarfs Vortex's marginal advantage over Parquet (~11%)." **Worth evaluating as a cold-store format only after the seam and coverage gates pass; it is a second bet, not the first.**
- **Polars.** Still no proper Decimal256/uint256 (issue #15443 open); Decimal is 128-bit only and downstream tools (Cherry) cast uint256 to string/binary. Not usable for exact chain values.
- **Lance/LanceDB** (ML/vector, versioned datasets) and **Iceberg-rust** (table format over DataFusion) are off-target for exact-integer OLAP. **glaredb** is rebuilding its own engine off DataFusion; **Sail** extends DataFusion with a custom chumsky-based parser for Spark SQL; **Comet/Blaze/Gluten/Auron** are Spark accelerators. None handle 256-bit exact integers natively.
- **Feldera/DBSP.** MIT-licensed, mechanically-verified incremental computation; ships `feldera-fxp` fixed-point decimal and a SQL-to-DBSP compiler. Nuthatch *already* depends on the `dbsp` crate for RFC-0041 (and pins Rust 1.95.0 because `dbsp` hits a next-solver ICE on 1.97) — this is the natural tie-in for maintained incremental views inside Burrmill.

### Design directions where Burrmill can be strictly better

- **(a) Exact 256-bit arithmetic as a first-class type, refuse-on-overflow.** *Highest win, lowest generic-engine competition.* Build on arrow i256/Decimal256; represent values as exact integers, carry a high word through partial sums, and return `BurrmillError::Overflow` rather than NULL/wrap. This eliminates the `_dec`/`_overflow` VARCHAR hack entirely and makes Burrmill a *better* reference oracle than DuckDB (which wraps threaded HUGEINT sums). Feasibility high (slice 1 already does the fold path); effort moderate; win: strict correctness DuckDB cannot match.
- **(b) Exploit sealed-immutable segments.** No MVCC, no buffer manager, no WAL. Precompute per-segment zone maps (min/max block_number, log_index — segments are already sorted by block_number then log_index), Bloom filters (already written on address+hash columns, zstd level 3), and optionally materialized aggregates and decoded-column caches keyed by content hash. Feasibility high (the data is already sorted and content-addressed); win: skip DuckDB's generic pruning overhead and the #1183 rebind cost.
- **(c) Native redb hot-tip scan source.** Make the redb tip a first-class scan operator instead of an FFI/Arrow bridge. Feasibility medium, risk high (the seam); win: removes the federation boundary Nuthatch currently pays.
- **(d) DBSP-maintained standing queries.** Reuse the `dbsp` dependency to answer RFC-0041 entities incrementally inside the engine rather than rescanning — the panel that went 2.15 s → 88 ms shows the ceiling. Feasibility high (mechanism shipped); win: standing queries answered incrementally.
- **(e) tokio-native execution, per-query memory budgets, cancellation.** A budget that does not depend on host core count (README: 145 MB @ 1 thread vs 340 MB @ 32 threads is why 8 threads is the default, buying only 6% past that). Feasibility high; win: the concurrency story DuckDB's own thread pool fights.
- **(f) Compile-once-run-many plan cache keyed on query shape.** The admitted subset is tiny; cache the plan per shape and skip parse/bind/plan per request. Feasibility high; win: kills the #1183 class of overhead structurally.
- **(g) Chain-specific operators.** Address/topic decoding, ABI-aware decoding, log filtering pushed into the engine. Feasibility medium; win: work DuckDB can't specialise.
- **(h) Deterministic results across threads.** Essential for the reference-oracle role; the partial-sum fold already produces order-independent exact results. Feasibility high; win: DuckDB is *not* deterministic here (the threaded wrap).
- **(i) Binary size / startup / build / cross-compile / WASM.** Pure Rust removes the C++ blob, libstdc++ linkage, and the WASM blocker — but burrmill#1 is the honest counter-gate: monomorphised generic operators can bloat the *consumer's* build worse than a cached `libduckdb.a`, and there is "no equivalent knob for instantiations that happen in the caller." Keep the public API concrete (non-generic entry points over Arrow `RecordBatch`) so operators instantiate once in Burrmill's rlib, not per consumer.

### Benchmark strategy

A fair Burrmill-vs-DuckDB benchmark for Nuthatch must be workload-derived and refuse to measure only Burrmill's strengths:
- **Workload from real queries.** Derive the shape mix from the Lodestar/allocations dashboards' 47 distinct statements and the RFC-0041 entity shapes (netted sums, ROW_NUMBER newest-row picks), not synthetic folds alone. Weight by actual `/sql` frequency.
- **Hold all engines to the same budget.** The README already does this right: same thread count (8), same 256 MB RSS ceiling, parity verified *before* timing on every configuration. Keep that discipline — "a budget that depends on the host's core count is not a budget."
- **Cold vs warm and many-small-segment layouts.** Test the nest-shaped bimodal segment-size fixture at 100 and 10,000 segments (where DataFusion collapses to 3.6×), and run both page-cache orderings so a ratio that survives both is about the engines, not the cache.
- **Correctness/differential on overflow edges.** Keep the generated corpus against DuckDB *and* DataFusion oracles, including the answerability-divergence cases (where engines disagree whether a query is answerable at all), and the `TRY_CAST` divergence table.
- **Include the parts Burrmill loses.** Measure fixed cost honestly (the README's `UNSAFE_fixed_duck=NNpct` field when the ratio is mostly fixed cost is the right instinct), measure build footprint per burrmill#1's four figures (cold `target/`, querying test binary, non-querying test binary, consumer incremental rebuild), and include at least one shape Burrmill must *delegate* so the delegation cost is visible.

### Honest assessment: where DuckDB stays ahead

DuckDB's optimizer maturity, vectorized-operator breadth, join algorithms, full SQL coverage, and ecosystem (extensions, tooling, the whole `duckdb-rs` surface) are not things a solo-maintained engine beats — the README concedes this ("nobody solo-maintains a better SIMD kernel library"). Nuthatch already proved a general Rust engine (DataFusion) loses 1.6–2.7× on the fold that matters. Therefore the strategically correct target is **beat DuckDB on the admitted subset and delegate everything else** — exactly Burrmill's stated posture. Full replacement is only justified if the coverage ratchet (RFC-0044 §4.6) reaches the point where the admitted subset covers essentially all real nest traffic *and* the DataFusion fallback can be removed (slice 7), which is also the build-footprint terminal state.

**What would justify reopening RFC-0042:** the 2026-08-30 decision correctly kept DuckDB and parked the question. The evidence that should reopen it, in order: (1) Burrmill demonstrates the hot/cold seam (redb ∪ sealed) at parity — currently cold-only; (2) Burrmill clears the build-footprint gate (burrmill#1) against `libduckdb-sys` at `-g0` on cold `target/`, one-integration-test-binary size, and consumer incremental rebuild time; (3) Burrmill covers the top ~5 real dashboard shapes at parity. RFC-0042 §14 found only two of seven expected wins (disk, binary size) actually materialised from dropping DuckDB, so the correctness and footprint wins — not raw speed — are the real case, and the gates should measure those first.

## Recommendations

1. **Report the DuckDB threaded-HUGEINT-SUM wrap upstream now**, independent of the Burrmill decision. It is a silent-wrong-answer in a financial context, and Nuthatch relies on DuckDB as its RFC-0041 reference oracle; a wrapping oracle is a correctness risk to the whole authored-entity mechanism. Pin it to `libduckdb-sys 1.10501.0` (DuckDB 1.5.1) with the two-file/two-thread `MAX, +1` repro. Threshold to escalate: if the wrap reproduces on current stable (1.5.5), it becomes a blocking correctness argument for Burrmill's oracle role.
2. **Prioritise the exact-256-bit type system (design direction a) as Burrmill's slice-2 headline**, because it is the win with the least competition from any generic engine and it retires the `_dec`/`_overflow` hack. Build on arrow 60.x i256/Decimal256.
3. **Make the build-footprint gate (burrmill#1) a release-blocking CI check from slice 2**, measured on a throwaway consumer crate with a realistic integration-test-binary count, publishing all four figures per release alongside the coverage ratio. Do this before the surface widens — the number only gets harder to move.
4. **Tackle the hot/cold seam (direction c) next, with a written invariant and a differential test against DuckDB's hot∪cold answer**, since it is both the highest-risk item and the precondition for any RFC-0042 reopen.
5. **Keep DataFusion strictly behind an off-by-default feature flag** as the delegation fallback, never in the default dependency graph, so a nest running only owned shapes never compiles it.
6. **Do not reopen RFC-0042 until gates (1)–(3) in the assessment all pass on the real dashboard workload.** Benchmarks on synthetic folds alone are not sufficient evidence. Benchmark that would flip the decision: the admitted subset covering ≥90% of measured `/sql` traffic at ≤1.0× DuckDB across cold and warm, on the seam, under the same RSS budget, with build footprint at or under `libduckdb-sys` `-g0`.

## Caveats
- The brief's stated Nuthatch version (v2.5.x) is stale; the live repo is at v3.8.3. Architecture (redb hot / sealed Parquet cold / DuckDB SQL) is unchanged, but specific issue numbers and config keys reflect the 3.x line.
- The DuckDB threaded-SUM wrap is corroborated by Burrmill's own corpus and consistent with a third-party ClickBench finding (a 2^64-multiple discrepancy on a *development* build, tamnd/rudb-compat #12), but I could **not** find it as an open issue in the official `duckdb/duckdb` repo; DuckDB's documented policy is to error, and PR #15040 shows the team actively guarding HUGEINT/UHUGEINT sums. Treat it as a likely-unreported gap, not an acknowledged bug.
- Burrmill's benchmark numbers (0.38–0.87× DuckDB across fourteen configs, 210 MB at 989,690 groups) are self-reported from its own harness on one plan shape and a synthetic nest-shaped fixture; they are reproducible (`cargo run -p burrmill-bench`) but not independently verified and cover only cold segments, not the hot/cold seam.
- Several ecosystem performance figures (Vortex 100–200× random access, DataFusion's ClickBench lead) are vendor/community benchmarks on general workloads and do not transfer directly to Nuthatch's many-small-segment, exact-integer shapes; DataFusion's own tracker acknowledges the ClickBench lead has since been retaken by DuckDB.
- RFC-0042, RFC-0044, and RFC-0013 full texts were not directly fetchable; their content here is reconstructed from the READMEs, burrmill#1, docs.rs, release notes, and issue threads that quote them. Section-level claims (e.g. RFC-0044 §4.6 slice 7, RFC-0042 §14) should be verified against the source files before being cited as load-bearing.
- Note there is an unrelated older project also named "BurrMill" (Kaldi/GCP compute suite, github.com/burrmill/burrmill) and an unrelated Nuthatch RFC-0044 (subgraph-port skill) *inside the Nuthatch repo*; the Burrmill engine's own RFC-0044 is a separate document in the burrmill repo. Do not conflate them.
